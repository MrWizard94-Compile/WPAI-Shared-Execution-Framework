## C. Protocol and SDK decision

Use **local stdio with a dual-era handshake** for the next compatibility slice. The observed Grok path requires the legacy initialization route used in the fixture. Antigravity used the July 2026 discovery path. Codex and Claude exercised both paths, with Claude’s modern evidence limited to connection and discovery. A July 2026-only primary artifact would exclude the exact Grok profile tested. A legacy-only artifact has not been validated with Antigravity. Keep one core, operation contract and server build while negotiating the dialect per client. [Legacy MCP lifecycle](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle), [July 2026 MCP versioning](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning), [Modern stdio compatibility](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/stdio).

The spike used **Python 3.14.3 standard library** for the small dual-era subset. This avoided SDK installation and gave direct control over the negotiation evidence. The installed Python MCP SDK **1.26.0** independently connected and echoed over `2025-11-25`. It is a verified legacy client control. Production should evaluate an installed or approved dual-era SDK against the exact matrix before choosing it. Official Python v2 advertises legacy and modern transport support, but no Python v2 implementation was installed or exercised here. No evidence justifies a separate Rust, TypeScript or Python package for each agent. [Python SDK protocol support](https://py.sdk.modelcontextprotocol.io/protocol-versions/), [Codex MCP test entry points](https://github.com/openai/codex/blob/6ff1e1ca3b30fc8b914720681fcf5fe62e95f856/scripts/mcp_conformance/run_codex_compliance.py), [Claude runtime selection](https://code.claude.com/docs/en/mcp), [Gemini health-check implementation](https://github.com/google-gemini/gemini-cli/blob/v0.71.1/packages/cli/src/commands/mcp/list.ts).

## E. Security and isolation

- This server uses synthetic data and stdio only. It has no network listener, filesystem operation, provider secret, shell command or arbitrary execution endpoint. The launcher provides a minimal environment, caps child lifetime at 60 seconds and records only bounded server events. Stdout is reserved for JSON-RPC and diagnostics go to stderr. Frame reads are capped at 8,192 bytes and a process accepts at most 128 messages.
- The server rejects an unauthorized operation before validation or dispatch into any action. Direct tests, Codex and the signed-in Antigravity tool call independently observed `DENIED` and **zero protected actions**. Client-side validation in Antigravity blocked malformed payloads before transmission, while the server protections were exercised independently through Codex and the wire driver.
- Client profiles used disposable homes. After the director signed in, Antigravity’s live test used the existing session, a disposable workspace, ACP-only MCP registration and separately named Antigravity app data. The test driver allowed only one-time approvals from the synthetic tool catalog. It verified that the checked normal settings stayed unchanged. During a live call the probe PID had zero TCP listeners. No probe PIDs remained after final verification.
- No production repository or agent MCP configuration was edited for the fixture. No public endpoint, tunnel, service or framework was created. The tests establish process and contract behavior for this fixture. They do not establish OS-level sandbox guarantees for a future production executor.

## G. Recommended Stage 1 gate and minimum scope

Before production implementation, obtain native echo, invalid-input and explicit-denial evidence from Grok and Claude using the same probe and an approved authentication or direct-call route. Verify the effective Grok policy permits the isolated launch and preserve the proof across default and intended headless modes.

The smallest useful Stage 1 would then implement **one typed, read-only `repo_health_v1` operation**. It should target one allowlisted existing checkout and one mapped canonical GitHub repository. It should emit the twelve W1 facts in a bounded structured result with matching text, source URLs/refs, clear unavailable statuses and an optional caller-bound evidence cursor. Keep Git and GitHub orchestration in a single local core, with one dual-era stdio adapter and four launch configurations. Require identical values against the independent W1 oracle, zero writes, and denial before subprocess creation. Measure comparable latency and operation counts before adding caching, HTTP, background tasks or new operations.
