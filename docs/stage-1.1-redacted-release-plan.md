# Proposed redacted release plan

This proposal requires separate authorization. Stage 1.1 preserves the existing public evidence and history.

1. Inventory the exact public tree, candidate archive members, original hashes, authorized retention locations and disclosure approvals. Keep a private crosswalk from original observations to approved public records.
2. Build new evidence copies with a synthetic repository, stable placeholders for paths and session identifiers, and coarse hardware classes. Retain protocol revisions, operation schemas, observable timing units, test counts, denial states and shutdown outcomes.
3. Keep unaffected code byte-identical. Regenerate manifest hashes for transformed files and nested packages. Two fresh builds must match byte for byte. Verify the extracted file manifest and exercise the release’s CLI, transport and tests.
4. Inspect exact candidate blobs, ZIP members and archive metadata for credential and identifying data. Review the diff against the approved disclosure scope. Record the source commit, original and public hashes, transformations, and any tests whose historical inputs no longer match the public copies.
5. Decide independently how to handle already public history. A new redacted release leaves existing historical objects visible. Any visibility change, history remediation, credential response or cleanup requires its own approved plan and verification.
